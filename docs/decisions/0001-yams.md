# 0001: YAMS behind the Arm IO

Status: **recommendation written, decision pending (Cohen).** Nothing was
changed to make YAMS the default; `plain` is still the default IO.

## What was tried

`ArmIOYams` implements the existing `ArmIO` with YAMS 2026.11.06 (a
`TalonFXWrapper` and `yams.commands3.mechanisms.Arm`). One class serves both
the real robot and simulation. `RunProfile` picks it with `ARM_IO=yams`
(default `plain`). `Arm.java` and both scenarios did not change.

## Lines of code

Counted without blank lines, comments and imports.

| Plain | Lines | YAMS | Lines |
| --- | --- | --- | --- |
| `ArmIOSim` | 52 | `ArmIOYams` | 49 |
| `ArmIOTalonFX` | 37 | | |
| Total | 89 | Total | 49 |

YAMS replaces two classes with one. The plain sim also has a PID loop and a
physics model that YAMS provides.

## Evidence

Run with `frc sim`, `frc replay` and `frc log` on a Mac, real-time pacing.

| | Plain | YAMS (kP 15 V/rad, kD 0) |
| --- | --- | --- |
| `ArmReachesGoal` | pass, 11 loops to goal | pass, 22 loops to goal |
| `ArmHoldsWithinLimits` | pass | pass |
| Replay, `Arm/GoalRad` | no divergence | no divergence |
| Replay, `Arm/AtGoal` | no divergence | no divergence |
| Same scenario twice, position stats | not identical | not identical |

"Not identical" for both: the mean position differed by about 1% between two
runs (plain 0.7453 vs 0.7520; YAMS 0.6876 vs 0.6795). Commands v3 waits use
the real clock while the physics steps a fixed 20 ms per loop, so timing
jitter shifts when the arm moves. This is not caused by YAMS.

YAMS with the gains that were stable for plain (40 V/rad, kD 0.2) passed
`ArmReachesGoal` but failed `ArmHoldsWithinLimits`: the arm oscillated across
both hard limits (-0.20 to 1.60 rad). Stable gains were found by trying 40, 15
and 8 V/rad with kD 0 and 15 with kD 0.05; 15 and 8 were stable. The likely
cause is that the TalonFX control loop runs much faster than the 20 ms steps
at which YAMS updates the simulated rotor, but that was not confirmed.
The slower time to goal (22 vs 11 loops) is at the lower gain and is not a fair
comparison of the libraries.

## What YAMS needed that plain did not

- **A `Mechanism` reference.** `yams.commands3.mechanisms.Arm` reads a
  `Mechanism` from its config and throws if it is missing. YAMS uses it only
  to register live-tuning commands. The IO does not own one, so
  `ArmIOYams` passes an unregistered placeholder (`new Mechanism() {}`). The
  core `Arm` class has a protected constructor, so it cannot be used
  directly.
- **Different gains.** See above. The units also differ (volts per mechanism
  rotation, not per radian).
- **Calling `simIterate()` ourselves.** YAMS does not step its simulation on
  its own; `ArmIOYams.updateInputs()` calls it in simulation.
- **Extra libraries.** None for the TalonFX path. The build resolves only
  `YAMS-core`, `YAMS-commands3` and the CTRE API that was already present.
  YAMS also contains Spark and Thrifty wrappers, which would need REVLib or
  ThriftyLib on the classpath if used. They are not used here.

## Anything that broke or surprised

- Phoenix writes a timestamped signal-log folder under `logs/` for every run
  that uses `ArmIOYams` (13 MB after about 12 runs). `logs/` is git-ignored.
- From reading the source (not measured): YAMS creates and publishes its own
  `Mechanism2d` and telemetry to NetworkTables. These are not part of the
  AdvantageKit log.
- `ArmIOYams` has never run on hardware, like `ArmIOTalonFX`.
- This was the simplest mechanism (one motor, one joint). It says little
  about YAMS for elevators, flywheels or multi-motor mechanisms.

## Recommendation

**Keep it as an option, not the default.** It cuts the IO code by about 45%
and one class covers real and sim, and it replayed correctly. But it needs its
own tuning, a placeholder `Mechanism`, and hardware testing before the team can
rely on it, and the plain IO is just as small once written. Revisit after the
first real mechanism (M6 swerve or a second arm-like mechanism) shows whether
the saved code is worth the extra surface.

If Cohen decides otherwise:

- **Make YAMS the default:** change the default in `RunProfile.armIO` and add a
  line to `AGENTS.md` that standard mechanisms use `XIOYams` and unusual ones
  use hand-written IO.
- **Drop YAMS:** delete `ArmIOYams`, remove the `ARM_IO` switch and the
  `YAMS_*` constants, and have a human uninstall the YAMS vendor library
  (`vendordeps/yams_commands3.json`).
